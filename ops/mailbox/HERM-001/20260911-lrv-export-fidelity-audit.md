# LRV_PLUS export fidelity audit

> **Parent reconciliation (2026-09-11, post-audit):** The initial comparison was against unmerged `origin/main`/task commit. The current worktree now preserves the current-main ExcelJS freeze/provenance/RESURS_VEDOMOST path while integrating the seven-category `J:P` contract, shifted `Q:X` fact/F2 formulas, `Y/Z` hidden service columns, and non-zero `БЕЗСКЛАД` nakrutka coverage. Final local evidence: focused LRV suite `33/33`, full clean-install suite `68/524`, app typecheck PASS. Exact byte-for-byte T1 visual parity and owner-generated artifact review remain separate/unproven.

**Scope.** Read-only comparison of `origin/main` (`5e7a1af`) with candidate task commit `9a1b5b2`, against T1 `Smeta tizimi/00_Config.js` and `10_Engine.js`. `9a1b5b2` is not merged into `origin/main`. Only this report was written.

## Findings

1. **J:P contract — PROVEN in T1; MISSING in latest main; PARTIAL in candidate.**
   - T1 defines J:P as `ЧЕЛ, МАШ, МАТ, ОБ, БЕЗСКЛАД, М/К, КАБ` (`Smeta tizimi/00_Config.js:13-20,41-49`) and writes the display headers `ЧЕЛ, МАШ, МАТ, ОБ, БЕЗ СКЛАД, М/К, ПРОВОД` (`Smeta tizimi/10_Engine.js:1542-1548`).
   - Latest main exports only J:O, with N=`КАБ`; P and `БЕЗ СКЛАД` are absent (`frontend/src/lib/lrv-plus-export.ts:181-188,299-305`). Its category totals also iterate only J:O (`frontend/src/lib/lrv-plus-export.ts:626-629`).
   - Candidate `9a1b5b2` adds a separate N bucket and P position, but emits P as `ПРОВОД/КАБ`, not the requested exact `ПРОВОД` (`frontend/src/lib/lrv-plus-export.ts@9a1b5b2:72-84,206-212`; test expectation: `frontend/src/lib/lrv-plus-export.test.ts@9a1b5b2:113-120`). Normalization does accept `КАБ`/`ПРОВОД` (`...@9a1b5b2:78-84`).

2. **Quantity formula fidelity — PARTIAL / material mismatch.** T1’s generated formula is `F(rs)=E$<blRow>*E<rsRow>` (`Smeta tizimi/10_Engine.js:721-728`; sample formulas are visible in `_f2lab/_unz/Amfiteatr_-_109993_ALL_01-01______________________LRV_PLUS.xlsx/xl/worksheets/sheet2.xml:1`). Both latest main and candidate emit `E<row>*F<parentRow>` (`frontend/src/lib/lrv-plus-export.ts:241-245`; `frontend/src/lib/lrv-plus-export.ts@9a1b5b2:132-136`). Their tests lock in that different formula (`frontend/src/lib/lrv-plus-export.test.ts:46-54`; `...@9a1b5b2:193-199`).

3. **Live formulas and known cached values — PROVEN for the tested latest-main path.** Latest main writes leaf `H=F*G`, parent `SUMIF` formulas, root-only `ЖАМИ` formulas, and `.v` caches when values are known (`frontend/src/lib/lrv-plus-export.ts:247-296,594-606,610-620`). The current focused run passed: **1 file, 31 tests passed** (`CI=1 npx vitest run src/lib/lrv-plus-export.test.ts --reporter=dot`). Tests verify formula text and cached H/FAKT/F2/totals (`frontend/src/lib/lrv-plus-export.test.ts:224-269`).

4. **NULL/blanks — PARTIAL.** Latest main preserves unknown leaf/parent H values as `null`/no cached value (`frontend/src/lib/lrv-plus-export.ts:247-258,270-286,567-576`), but category aggregation converts an unknown category sum to numeric zero (`q.summaQiymat ?? 0`) and writes that cache (`frontend/src/lib/lrv-plus-export.ts:539-542,626-629`). Full-mode derived AOA cells still use `''` before formula replacement (`frontend/src/lib/lrv-plus-export.ts:582-606`). Current tests cover the in-memory null and known export paths, not an exported unknown category’s cell type (`frontend/src/lib/lrv-plus-export.test.ts:72-82,224-269`). Candidate improves unknown category totals but still uses string blanks in AOA (`frontend/src/lib/lrv-plus-export.ts@9a1b5b2:233-235,263-275`; test only checks `v ?? ''`: `...@9a1b5b2:140-152`).

5. **Totals / double-count — PROVEN for root monetary totals; PARTIAL for full category fidelity.** Latest main sums only `daraja=0` roots (`frontend/src/lib/lrv-plus-export.ts:291-296`) and tests assert that shape (`frontend/src/lib/lrv-plus-export.test.ts:103-108`), so descendants are not added a second time when the tree levels are valid. T1 explicitly uses leaf-only formulas for its stored resource totals to avoid leaf+razdel double counting (`Smeta tizimi/10_Engine.js:1506-1534`). Latest main’s H/T/U/V/W totals therefore have the right anti-double-count strategy, but the J:O-only category/nakrutka path cannot represent the required N/P buckets (`frontend/src/lib/lrv-plus-export.ts:717-725`).

6. **Styles / widths — PARTIAL.** The row palette matches T1’s `rz` yellow, `bl` blue/white, and `mat` green (`Smeta tizimi/00_Config.js:62-65`; `frontend/src/lib/lrv-plus-export.ts:342-347`; tests: `frontend/src/lib/lrv-plus-export.test.ts:276-299`). It is not byte/style-fidelity: T1 uses a dark-blue white header and `#,##0.####` numeric format (`Smeta tizimi/10_Engine.js:1535-1558,800-804`), while latest main uses gray header, medium/thin borders, wrapping, and `#,##0.00` for money (`frontend/src/lib/lrv-plus-export.ts:632-680,642-667`). `if (!cell) continue` means null/absent cells do not receive the same borders/styles as populated cells (`...:649-661`). Widths are hard-coded in latest main (`...:694-713`) and differ from the inspected T1 workbook’s sheet2 width records (`.../xl/worksheets/sheet2.xml:1`); exact width parity is not proven.

7. **Autofilter / grouping — PARTIAL against T1, PROVEN in latest-main implementation.** T1 removes an inherited filter and does not recreate a complete LRV filter in the inspected engine path (`Smeta tizimi/10_Engine.js:558-562`). A T1 LRV artifact has a filter limited to `$A$11:$F$4999` and no row outline metadata (`.../Amfiteatr_-_109993_ALL_01-01______________________LRV_PLUS.xlsx/xl/worksheets/sheet2.xml:1`). Latest main creates `A2:<last-column><last-row>` autofilter and writes outline levels (`frontend/src/lib/lrv-plus-export.ts:682-686,714-715`); the current test suite verifies outline XML but not filter range (`frontend/src/lib/lrv-plus-export.test.ts:127-144`).

8. **Freeze panes — PROVEN, but not T1-fidel.** T1 freezes 29 columns and 7 rows (`Smeta tizimi/10_Engine.js:553-556`). Latest main uses ExcelJS after SheetJS to freeze only the first 3 columns and 3 rows on LRV_PLUS, and one row on the resource sheet (`frontend/src/lib/lrv-plus-export.ts:784-801`); the focused tests pass for `xSplit=3,ySplit=3` (`frontend/src/lib/lrv-plus-export.test.ts:183-194`). This is a deliberate behavior difference, not an exact T1 match.

9. **`>=1000` rows — PARTIAL / end-to-end UNPROVEN in latest main.** The T1 artifact contains 4,999 LRV rows and 51,682 formula cells (`.../Amfiteatr_-_109993_ALL_01-01______________________LRV_PLUS.xlsx/xl/worksheets/sheet2.xml:1`). Latest main has no explicit row cap and loops the supplied rows (`frontend/src/lib/lrv-plus-export.ts:197-217,566-590`), but its current tests contain no 1000/1001-row case. Candidate adds a static 1001-resource anti-double-count test (`frontend/src/lib/lrv-plus-export.test.ts@9a1b5b2:279-306`), but that unmerged candidate test was not run here.

10. **Provenance / period metadata — PARTIAL in latest main; MISSING in candidate.** Latest main accepts object/project/period/source/revision/completeness context (`frontend/src/lib/lrv-plus-export.ts:107-131`), gates company/object/read completeness (`...:160-167`), and writes an optional `МАНБА` sheet with object IDs, `Давр`, source document, revision, checksum, and UTC creation time when provenance fields are supplied (`...:752-779`). It does not require or always emit period/provenance; the gate deliberately allows missing source/revision/checksum (`...:142-167`; tests: `frontend/src/lib/lrv-plus-export.test.ts:473-510`). `lrvBelgiYoz` defines a machine-readable object/period marker but the export body does not call it (`...:314-327,511-802`). Candidate `9a1b5b2` has no context/provenance/period API or metadata sheet (`...@9a1b5b2:237-359`).

11. **Library capability / verification — PROVEN.** The frontend directly depends on `xlsx-js-style` 1.2.0 and `exceljs` 4.4.0 (`frontend/package.json:15-40`; installed package manifests: `frontend/node_modules/xlsx-js-style/package.json:2-5`, `frontend/node_modules/exceljs/package.json:2-4,73-96`). `xlsx-js-style` supplies SheetJS-style cell formats but not freeze panes; latest main documents the limitation and uses ExcelJS for the final pane write (`frontend/src/lib/lrv-plus-export.ts:784-790`). ExcelJS’s declared `views`, `frozen`, `split`, and `outlineLevel` capabilities align with the implementation (`frontend/node_modules/exceljs/package.json:73-96`).

## Bottom line

Latest main is operational for the tested six-category export, formula/cached-value path, outline grouping, and 3x3 freeze, but it is **not LRV_PLUS-fidelity complete**: required J:P is missing, the quantity formula differs from T1, unknown category values can become cached zeroes, T1 header/format/freeze behavior is not preserved, and >=1000-row and always-on provenance/period behavior remain unproven/optional. Candidate `9a1b5b2` addresses the separate N/P shape and adds a 1001-row test, but still has the T1 quantity-formula mismatch, the non-exact P label, no freeze/provenance, and was not merged or executed here.
