# HERM-001 — existing-object smeta re-import audit

> **Parent reconciliation (2026-09-11, post-audit):** The audit conclusion remains current: the shipped UI is diff-preview/non-destructive and does not silently clear an existing smeta. Dependent-data refusal and destructive re-import are still owner/production-gated; no delete/reset was executed.

**Audit scope:** current working tree in `GAS_task_20260911`; the unmerged task-side `9a1b5b2` is cited separately and is not treated as delivered.

**Runtime boundary:** **[BLOCKED]** This was a static source/migration audit only. No browser, production, live Supabase, or destructive operation was used. No test command was run. No product code, Git state, or production state was changed; only this report was written.

## Findings

1. **[PROVEN server / PARTIAL UX] `SMETA_ALREADY_EXISTS` is enforced in both import paths.** `t2_smeta_import_boshla_v1` checks object ownership and refuses when any canonical `t2_qator` exists (`supabase/migrations/20261019090000_t2_smeta_import_bolakli_v1.sql:119-136`); finalize repeats the check as a race guard (`:182-195`). The legacy bulk RPC has the same refusal (`supabase/migrations/20261010120000_t2_smeta_import_bulk_v1.sql:33-45`). The API dispatches start, chunk, finalize, and cleanup operations (`frontend/functions/api/smeta-yukla.ts:232-236`). The current page handles the code at start/finalize (`frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:1072-1081, 1109-1115`) and pre-filters objects with `qator_soni` (`:1141-1157`). The pre-filter is only advisory; the database guard is the authoritative protection.

2. **[MISSING current] Existing-object re-import UX is not wired as an actual diff/import flow.** The current page says a new file is only a “non-destructive diff preview” (`frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:1155-1157`), but the page import list at `:3` does not import the re-import diff helper, and the file input is rendered only when `!alreadyHasSmeta` (`:1177`). Thus an existing object gets a warning, not a usable preview result or controlled re-import action. `SmetaYuklaNative.test.ts` contains no existing-object, cleanup, or required-error-contract assertion (`frontend/src/admin/sahifalar/SmetaYuklaNative.test.ts:1-549`).

3. **[MISSING current / PARTIAL unmerged candidate] Explicit destructive confirmation is absent from the effective UI/backend contract.** The current request body for `smeta_tozala` has only company, object, and operation identifiers (`frontend/functions/api/smeta-yukla.ts:80-86`), and the handler forwards the call directly (`:205-211`); there is no server-verifiable confirmation field. The current page has no cleanup caller or confirmation path. The unmerged task-side candidate does add a browser `confirm()` with a destructive warning (`9a1b5b2:frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:386-404`), but that code is not in the effective current page and cannot be counted as delivered.

4. **[PROVEN backend / MISSING current UX] `SMETA_HAS_DEPENDENT_DATA` is a hard refusal for the dependencies explicitly checked.** The effective cleanup function checks `t2_akt_qator` and `t2_price_basis_line` and returns `SMETA_HAS_DEPENDENT_DATA` before any delete (`supabase/migrations/20261021140000_t2_smeta_tozalash_bulk_fix_v1.sql:34-52`). Deletes occur only afterward (`:55-78`), so these refusal branches do not partially clear the object. The current frontend has no handler for this code. The unmerged candidate would convert it into a terminal UI block and hide the cleanup action (`9a1b5b2:frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:391-398`); that behavior is not merged.

5. **[PARTIAL] Sequential retry/idempotency is designed, but atomic/concurrent behavior is not proven.** The current page creates separate source/import operation IDs (`frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:830-832`) and reuses the import ID through start/chunk/finalize (`:1063-1106`). Start replays a logged result or reopens the same session (`supabase/migrations/20261019090000_t2_smeta_import_bolakli_v1.sql:108-116`); chunk retries overwrite the same `(sessiya_id, bolak)` primary key (`:160-171`); finalize replays the command-log result (`:186-195, 263-268`). Cleanup also reads/writes the command log (`supabase/migrations/20261021140000_t2_smeta_tozalash_bulk_fix_v1.sql:28-34, 73-78`). However, cleanup performs the prior-result lookup before authorization/object validation and has no visible lock around lookup plus insert (`:28-34, 76-78`), so cross-context replay can return a prior result and concurrent duplicate calls are not shown to have a stable response contract.

6. **[PARTIAL] Tenant/object ownership is enforced on the normal API path, but session-actor ownership is incomplete.** The API authenticates the cookie session and derives `actorId` server-side (`frontend/functions/api/smeta-yukla.ts:219-236`). Import requires a company membership with a write role (`supabase/migrations/20261019090000_t2_smeta_import_bolakli_v1.sql:86-95`), checks the object belongs to that company (`:119-123`), and scopes the source document (`:125-129`). The source-upload endpoint likewise derives the actor and passes company/object scope to its RPC (`frontend/functions/api/hujjat-yukla.ts:72-103`). But the import session records `actor_id` (`:132-134`), while chunk and finalize lookups constrain only `sessiya_id` plus `kompaniya_id`, not `actor_id=p_actor_id` (`:148-150, 182-184`). A different authorized writer in the same company can therefore operate another actor’s open session. Cleanup also checks the operation log before its membership/object checks (`supabase/migrations/20261021093000_t2_smeta_tozalash_v1.sql:28-34`). The cleanup function’s explicit service-role grant is present (`:76-77`); deployed privilege state for the chunked security-definer functions was not queried.

7. **[MISSING/PARTIAL] Current reset state is not demonstrated safe for object switching.** The object selector calls `reset()` and clears operation/document refs (`frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:1147-1150`), while the current reset implementation is at `:770-774`. The selector path does not itself clear the parsed workbook before the preview branch can render (`:1155-1157`), and there is no test asserting that switching from a populated object clears workbook, progress, sheet, resource, and error state (`SmetaYuklaNative.test.ts:1-549`). The unmerged candidate explicitly clears workbook and progress state (`9a1b5b2:frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:373-379`) and resets operation refs after cleanup (`:400-403`), but this is not current delivered behavior.

8. **[PROVEN static / BLOCKED runtime] Fresh import into an empty object has a complete canonical path.** The current page defines emptiness from `qator_soni` and exposes the file input only for an empty object (`frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:1141, 1177`), creates new operation IDs on file selection (`:830-832`), stores the source document, then starts the import with object/source scope (`:1050-1068`). The database validates the source document and creates the import session (`supabase/migrations/20261019090000_t2_smeta_import_bolakli_v1.sql:119-136`), then writes canonical rows and closes the session (`:237-268`). This is source-proven only; no live or browser execution was performed.

9. **[MISSING current caller / PROVEN backend caller] Cleanup has a backend endpoint but no effective product caller.** The only current product integration found is the `smeta_tozala` branch in `frontend/functions/api/smeta-yukla.ts:205-211, 232-236`. The current `SmetaYuklaNative.tsx` has no matching cleanup call; the visible cleanup call exists only in unmerged `9a1b5b2:frontend/src/admin/sahifalar/SmetaYuklaNative.tsx:391-392`. Consequently, the destructive backend contract exists, but current users cannot reach it through this page.

10. **[BLOCKED] Acceptance remains incomplete.** Static evidence proves first-import refusal, known-dependent-data refusal, source-document scoping, and sequential chunk retry mechanics. It does not prove the delivered existing-object UX, human-confirmed destructive path, dependent-data UI hard stop, reset correctness, deployed RPC privileges, or live idempotency/ownership behavior. The unmerged task-side implementation must not be treated as merged or verified until the merge conflict is resolved and targeted tests/browser plus non-production integration checks are run.
